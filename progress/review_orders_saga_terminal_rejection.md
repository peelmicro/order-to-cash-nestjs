## Claim-by-claim verification

**1. `nats-saga-commands.adapter.ts` exhaustive switch.** Read `RpcError['code']` in `packages/contracts/src/generated/asyncapi.types.ts` directly: 12 members (`VALIDATION_FAILED`, `NOT_FOUND`, `CONFLICT`, `PRECONDITION_FAILED`, `ORDER_NOT_CANCELLABLE`, `STOCK_UNAVAILABLE`, `INVOICE_NOT_PAYABLE`, `PAYMENT_MISMATCH`, `DOMAIN_ERROR`, `INTERNAL_ERROR`, `UNAVAILABLE`, `TIMEOUT`). `isTerminalRpcErrorCode`'s switch covers all 12 (9 terminal + 3 transient) with a `default: { const exhaustive: never = code; throw ... }` compile-time guard — confirmed genuinely exhaustive, not just by eye but because `apps/orders` typecheck passes with this `never` assertion in place (if the union grows, `tsc` fails here first). Read `apps/fulfillment/src/presentation/rpc-error-mapper.ts` and `apps/billing/src/presentation/rpc-error-mapper.ts` directly: both use `INTERNAL_ERROR` exclusively as the unmatched-error fallback (`error instanceof Error ? error.message : 'an unexpected error occurred'`) — never for a named domain/application error. This confirms the implementer's reasoning: `INTERNAL_ERROR` is genuinely "something unexpected happened on the responder side," not a business refusal, so classifying it transient (retryable) is correct and consistent with how it's actually produced in both services that emit it.

**2. `saga-command-dispatcher.ts` short-circuit.** Read the `catch` block directly (lines 171–204): `SagaCommandBusinessRejectionError` is checked first, inside the `for` loop's first (and only, for this branch) iteration; on match it calls `store.markRejected`, logs, and `return`s `'rejected'` immediately — never reaching the loop's next iteration, the post-loop `delay()`, or `park()`. Confirmed a terminal rejection on attempt 1 short-circuits without burning `maxAttempts` — the implementer's own test asserts this precisely (`releaseStock` called exactly once, `delays` empty). Verified this claim by mutation (below), not just by reading the test.

**3. New `'rejected'` status, no migration.** Read `SagaCommandStore.markRejected`'s Drizzle implementation and `claimDue`'s actual query directly: `claimDue`'s `WHERE` is `(status='pending' AND created_at<cutoff) OR (status='parked' AND next_attempt_at<=now)` — a `'rejected'` row matches neither disjunct, so it is structurally, not incidentally, excluded from every future sweep claim. Read the schema file: `status` is `varchar('status', { length: 10 })`, and `'rejected'` is 8 characters — fits with no DDL change; confirmed no `ENUM`/`CHECK` constraint exists on the column (a plain `varchar`), so the claim that `drizzle-kit generate` produces no diff is structurally sound, not merely asserted.
