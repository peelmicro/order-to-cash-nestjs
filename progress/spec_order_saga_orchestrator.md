## 1. Shape of the spec, in one paragraph

The orchestrator is three `@EventPattern` Kafka consumers (group `orders.saga`, `fromBeginning`) dispatching explicit per-fact commands on the `@nestjs/cqrs` `CommandBus`; each fact `CommandHandler` is the whole transactional unit over the **existing, unmodified** `IdempotentConsumer`; the 13 facts are a declarative step table (pure, unit-tested fact × status); state transitions + dedup + outbox + a durable **pending-command row** commit in one transaction, and the owed NATS command is issued only after commit — via the post-commit `EventBus` → `@Saga` (`OrderSagas`) → `Issue…Command` hop — with 3 attempts, 500 ms ×2 backoff, 5 s per attempt; exhausted commands **park** in `saga_commands` and a sweeper retries them on a capped schedule indefinitely (the in-memory hop is the fast path, the pending row + sweeper the guarantee), which is also how the live stack's stranded `ORD-000007/8/9` orders (and every order placed before features 17–22 exist) behave and later self-recover. Integration proof runs against stub NATS responders + real Kafka/MySQL/NATS via Testcontainers.

## 5. Post-gate revision (2026-08-21)

The human approval gate ruled on the table above: **rows 1, 2 and 4–15 approved as written; row 3 OVERRULED** — `@nestjs/cqrs` IS adopted, as a directive (the Task document mandates the package; the assessment exists to demonstrate the mandated stack in a real distributed system). The spec was revised in place, as a revision only — no approved row was reopened; the durability design (`saga_commands` + sweeper, commit-before-issue, the SO4 retry numbers, `saga_ignored_facts`, the parked steady state for `ORD-000007/8/9`) is unchanged in every observable respect.

What changed, and where:

- `design.md` §5.5 (new) and §9 (rewritten): the composed architecture — `@EventPattern` → `CommandBus` (ten `Handle<Fact>FactCommand`s, handlers = the transactional unit, awaited before offset commit) → post-commit `EventBus` (five dispatch-owed application events) → `@Saga` class `OrderSagas` (five `ofType` streams) → five `Issue<Command>Command`s → dispatcher (NATS issue, `pending → sent`). The in-memory hop is the fast path; the durable pending row + sweeper is the guarantee (the sweeper calls the dispatcher directly, never the bus). §2 (file tree + class-provider wiring with explicit `@Inject(TOKEN)`), §3.2/§3.3 (the retry budget moves off the consumer thread; the `factCommandFor` map), §6.2, §10 (`@nestjs/cqrs` `^11` via the workspace catalog), §11 (three new unit-spec rows) updated to match.
- `requirements.md`: SO2 gains "without dispatching any command"; SO3's crash clause names the in-process hop and states the pending record — not the hop — is the guarantee; traceability gains the SO3 fast-path unit row (`order.sagas.spec.ts`). No renumbering.
- `tasks.md`: new group **CQ1–CQ4** (catalog + `CqrsModule.forRoot()`; fact commands/handlers; dispatch events/commands/handlers; `OrderSagas` + the unit test proving event in → command out and no-termination-on-error); E1/E2/E4 amended for the composition; **F6 now explicitly proves the crash-window composition** — a `pending` row committed with NO in-memory hop is still issued by a sweeper cycle; H3 names the one installed package. Task count 31 → 35.
- `CLAUDE.md`: one binding convention line added — application layers use `CommandBus`/`QueryBus`/`EventBus` handlers in every service (features 17–25 inherit this); the `@Saga` construct lives in Orders where the orchestrator is; durability never depends on the in-memory buses.

The §5.5 composition argument ("an in-memory bus is safe in a distributed saga iff it is only an optimisation over a durable queue that would deliver the same command anyway") is flagged as a README trade-offs entry for the eventual README pass. Status remains `spec_ready`; the human flips to `in_progress`.
