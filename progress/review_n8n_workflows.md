## Defects

### D1 — The `.99` engineering succeeds only ~50 % of the time, so the compensation ratio is half what is configured

`n8n/workflows/1-order-generator.json`, `engineerCompensation()`; identical copy in `n8n/workflows/4-burst.json`.

The function adjusts only the last line's `unitPrice` by some integer `k`, which moves the total by `k × quantity`. The residues of `k × quantity` mod 100 form the subgroup generated by `gcd(quantity, 100)`. When the line's quantity is 2, 4, 5, 6, 8 or 10 — six of the ten values `1 + Math.floor(Math.random() * 10)` can produce — the required delta is unreachable for **any** `k`, and the loop runs all 99 magnitudes in both signs and returns `false`.

Measured by running the committed function verbatim over 200 000 compositions against the real seeded price shape:

```
attempts 200000  engineered OK 101097 (50.55%)  MISS 98903 (49.45%)  claimed-ok-but-not-.99 0
=> effective compensation ratio at the configured 0.15 = 0.0758   (spec target 0.15)
=> effective at burst's 0.20                          = 0.1011   (spec target 0.20)
```

Why it matters: spec §3.2 is explicit that a miss should be a near-impossible edge case — *"a single-unit line whose price would go negative — impossible with the seeded catalogue, but checked anyway"* — and §3.3 promises the observable *"~15 % reaching `cancelled` with reason `credit_rejected`"*. `.env.example` documents `ORDER_GENERATOR_COMPENSATION_RATIO=0.15` as "Proportion engineered to total `.99`". It is not; it is the proportion *attempted*, and half of those silently fall through as ordinary orders. The whole stated purpose of this workflow — making compensation appear in a live feed unprompted at a watchable rate — is delivered at half strength.

The implementer's own live sample (2 engineered out of 21 accepted, ≈9.5 %) is consistent with 7.6 % and was reported as a success without the shortfall being noticed. That is the verification gap, not just the code gap.

Mitigating, and worth saying: the local assertion is never wrong. In 200 000 runs there were zero cases of the function returning `true` on a total that does not end in `99`. The failure is an honest undershoot, never an invalid or mis-priced order.

The fix stays inside §3.2's "at most 99 minor units spread over one line" budget: choose the line to adjust as one whose `quantity` is coprime with 100 (a quantity-1 line always is, and one can be forced during composition), rather than unconditionally taking `lines[lines.length - 1]`.

### D2 — Four documented environment variables are read by nothing

```
$ grep -c 'INTERVAL_SECONDS\|BURST_WEBHOOK_PATH' n8n/workflows/*.json
n8n/workflows/1-order-generator.json:0
n8n/workflows/2-payment-robot.json:0
n8n/workflows/3-stock-replenishment.json:0
n8n/workflows/4-burst.json:0
```

- `ORDER_GENERATOR_INTERVAL_SECONDS` — the trigger node hardcodes `{"interval":[{"field":"seconds","secondsInterval":45}]}`.
- `PAYMENT_ROBOT_INTERVAL_SECONDS` — hardcodes `minutesInterval: 2`.
- `STOCK_REPLENISH_INTERVAL_SECONDS` — hardcodes `minutesInterval: 5`.
- `BURST_WEBHOOK_PATH` — the webhook node hardcodes `"path": "otc-burst"`.

All four are listed in `.env.example` with their spec defaults and no indication they are inert. Editing any of them changes nothing. `progress/impl_n8n_workflows.md` claims "every tunable from spec §2.5/§3.4/§4.3/§5.3/§6.3 ... documented with its spec default" and does not disclose that four of them are decorative.

Spec §2.5's premise is *"Every knob is an environment variable read by the workflow, so a demo is tuned without editing JSON."* For the schedule periods — the single most likely thing anyone tunes before a recording — that is currently false.

Either wire them (an expression on the trigger parameter, since `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` is already set) or state plainly in `.env.example` and the README that the period lives in the trigger node and these four are documentation of the default only. Silently listing them as tunables is the one option that is not acceptable.

### D3 — The n8n container is handed every credential in `.env`, including MySQL root, in a spec that says it must hold none

`docker-compose.infra.yml:409` — `env_file: [.env]` on `n8n` (and again on `n8n-init`). Combined with `N8N_BLOCK_ENV_ACCESS_IN_NODE: "false"` (line 429), `N8N_BASIC_AUTH_ACTIVE: false` and port 5678 published to the host, any Code node authored in the unauthenticated UI can read them. Verified inside the running container:

```
MYSQL_ROOT_PASSWORD=otc_root_dev_password
JWT_SECRET=otc_dev_jwt_secret_change_me
MAILTRAP_PASSWORD=<real Mailtrap credential>
DB_MYSQLDB_PASSWORD=otc_app_dev_password
```

Spec §1: *"They hold no database credential and no broker credential, because they have nothing to connect to."* The four committed workflows are clean — this is a wiring defect, not a workflow defect — but the property the spec states as structural is not actually structural any more; it now rests on nobody writing a different Code node. The Mailtrap credential is a real one, per the human's own note that `.env` holds real credentials.

`N8N_BLOCK_ENV_ACCESS_IN_NODE: "false"` is genuinely required and well-found. The fix is not to revert it but to stop shipping the whole file: replace `env_file: [.env]` with an explicit `environment:` allowlist of the ~25 `OTC_*` / `ORDER_GENERATOR_*` / `PAYMENT_*` / `STOCK_*` / `BURST_*` / `GATEWAY_OPERATOR_*` / `N8N_WORKFLOWS_ENABLED` variables the workflows actually read. Every other service in `docker-compose.apps.yml` needs the whole file; this one needs 25 named values and is the only container that will execute arbitrary user-authored JavaScript.

### D4 — After the SQLite discovery, four statements still assert the MySQL story

The discovery itself is correct, independently confirmed, and genuinely valuable. Leaving the *behaviour* alone was the right call — retargeting at `postgresdb` adds a container and accepting `sqlite` means unpicking the MySQL wiring, and neither is a workflow-authoring decision. The flagging is where it falls short. These four still say something false:

1. **`.env.example:43`** — `MYSQL_DB_N8N=n8n`, no note. This file is squarely inside the feature's own file list and was edited heavily; a one-line comment cost nothing.
2. **`docker-compose.infra.yml:447-449`** — the healthcheck comment *"`/healthz/readiness` (not `/healthz`) also checks the MySQL connection"*. It does not; there is no MySQL connection. This sits four lines below the new comment block that explains exactly why.
3. **`docker-compose.infra.yml:445-446`** — `depends_on: mysql: service_healthy` on a service that never contacts MySQL. Harmless but now known-gratuitous, and unmentioned.
4. **`n8n-init`, newly written in this feature** — carries `DB_TYPE: mysqldb` plus all four `DB_MYSQLDB_*` values with no comment at all. This is not inherited debt; it is new configuration written after the author knew it was dead. Its practical cost is that every `pnpm n8n:import`, every `pnpm n8n:export` and every startup now prints `Invalid value for DB_TYPE - Invalid enum value ... Falling back to default value` as routine output — I saw it on all six of my runs. Normalised error text in tool output is how the next real error gets missed.

Also `infra/mysql/init/01-create-databases.sh:6` — *"a dedicated database for n8n so its workflow tables never mix with ours"* — creates and grants on a database that has zero tables and always will. That file is outside the feature's enumerated scope, so not editing it was correct; not *mentioning* it in `progress/impl_n8n_workflows.md`, when the whole point of the finding is which statements it invalidates, was not.

### D5 — Stock replenishment's low-stock branch was reachable and should have been closed

The disclosure is honest and the two things that *were* verified (the empty-result branch, and `POST /stock/replenish`'s request/response shape by hand) are the right two things. But this branch was forcible with the tooling already in hand: `ORDER_GENERATOR_COMPANIES` / `STOCK_REPLENISH_COMPANIES` exist precisely to narrow the blast radius, and a burst aimed at one company and one product would have driven an item below its `lowStockThreshold` well inside the ~50 orders already placed. `replenishCompany()` reads `res.items.length` off the response and that read has never executed. It is a demo workflow, so this alone would not fail the review — but with D1 and D2 also open it should be closed in the same pass.

### D6 — The burst aborts entirely on any error that is not 409/422

`n8n/workflows/4-burst.json`, `placeOne()` rethrows anything that is not `409`/`422`, and `runPool` awaits it inside `Promise.all`, so a single `401` — or a single non-retryable `4xx` — fails the whole burst and returns a 500 to the webhook caller with no tally. The order generator implements spec §2.1's single re-login and retry; the burst does not implement it at all, and spec §2.3's *"One bad item never aborts a run"* applies to all four workflows.

### D7 — The stack-specific port is baked into the portable files

All four JSON files fall back to `http://gateway:3001`. Spec §2.5 fixes the default at `http://gateway:3000` and §8 lists *"the environment-variable names and defaults"* among the things that do not change when porting to #8/#9. The compose file overrides `OTC_GATEWAY_URL` correctly so nothing is broken here, but a stack-specific value is now hardcoded inside the one set of files the spec says must be reusable verbatim. Low impact; trivially fixed; worth fixing precisely because §8 singles this invariant out.

### D8 — The auto-activation claim is right in substance, overstated in the README

`README.md` and `progress/impl_n8n_workflows.md` both state as fact that n8n 2.x's CLI `publish:workflow` does not take effect until a full server restart. I tested both trigger types:

- **Webhook (`otcBurst`)** — `n8n publish:workflow --id=otcBurst`, then `POST http://localhost:5678/webhook/otc-burst` returned **200 and executed** with no restart (`execution_entity` row 38). n8n prints the "restart required" warning anyway; the warning is wrong for webhooks.
- **Schedule (`otcOrderGenerator`)** — published, then waited 75 s against a 45 s interval. **Zero executions.** The claim holds.

So the conclusion is correct for the three workflows it actually governs, and the scope boundary is **honestly drawn, not quietly skipped**: feature 33's own acceptance criterion reads *"auto-imported on container startup"*, not auto-activated, and that is implemented and verified. Auto-activation would also be actively harmful right now, given the Phase 24 recording needs a quiet system. The only thing to change is the README's blanket phrasing — it should say *scheduled* workflows.

I restored both workflows to `active=0` afterwards and re-confirmed the webhook returns 404. My burst probe placed one order, `ORD-000033`.

## D1 — fixed, 100.00 %, and the orders are still valid

`engineerCompensation()` now sets `lastLine.quantity = 1` before computing `delta = mod100(99 - total)`. Since `gcd(1, 100) = 1`, adding `delta` to that line's `unitPrice` moves the total by exactly `delta`, so every residue is reachable and the result is always `≡ 99 (mod 100)`. The delta is non-negative, so the "would drive a price below 1" branch is genuinely unreachable and is correctly kept as a defensive `return false` rather than deleted.

My own measurement, 200 000 compositions each, function extracted verbatim from the committed files, catalogue pulled live from the Gateway's own `/catalog/products|retailers|companies`:

```
1-order-generator.json: attempts 200000  OK 200000 (100.00%)  MISS 0  claimed-ok-but-not-.99 0
                        mixed-currency 0  bad-qty 0  bad-price 0  maxUnitPriceDelta 99
4-burst.json:           attempts 200000  OK 200000 (100.00%)  MISS 0  claimed-ok-but-not-.99 0
                        mixed-currency 0  bad-qty 0  bad-price 0  maxUnitPriceDelta 99
```

Armed the fix away in memory (`lastLine.quantity = 1;` → nothing) and re-ran the identical harness — **11.36 %** and **11.18 %**. The probe kills, so the 100 % is a property of the committed code and not of my measurement. Note this armed figure is *lower* than the 50.55 % I measured against the original function: the old version searched all 99 magnitudes in both signs, the new one computes a single delta, so the quantity forcing is now load-bearing rather than merely helpful. That is fine — it is there — but it is worth recording that this function has no fallback search any more.

The R2 question the brief raised is answered directly: forcing `quantity: 1` changes only *that one line's* quantity, never the product set and never the currency. Across 400 000 engineered orders, zero had a product outside the order's own currency, zero had a non-positive or non-integer quantity or unit price. ### N1 — a note on the orphan check itself, not a defect in the feature

`progress/impl_n8n_workflows.md` offers a clean `PRAGMA foreign_key_check` as the evidence that the deletion left nothing orphaned. That check is real but it is weaker than it reads. I scanned **every** table in n8n's schema carrying a `workflowId` column and compared against the live workflow ids, and found four orphaned rows in `webhook_entity`:

```
probe                 POST  probeWorkflow01
test-order-gen        POST  testOrderGen
test-payment-robot    POST  testPaymentRobot
test-stock-replenish  POST  testStockReplenish
```

`PRAGMA foreign_key_check` cannot see these — `PRAGMA foreign_key_list(webhook_entity)` returns `[]`, so the table declares no foreign key at all. Three things make this an observation rather than a defect:

1. They are **inert**. All four paths return `404`, as does `otc-burst`'s own stale row while its workflow is inactive. n8n registers webhooks from active workflows at runtime; these rows are dead bookkeeping.
2. They are **not from this fix pass**. They correspond to `PROBE` / `TEST - order generator` / `TEST - payment robot` / `TEST - stock replenishment`, still visible by name in `insights_metadata` with their `workflowId` nulled by n8n's own `ON DELETE SET NULL` — that is the original implementation session's scaffolding, not the review-fix session's, whose only throwaway (`otcTestIntervalExpr`) left nothing at all.
3. They live in the `n8n_data` Docker volume — this machine's runtime state, not a committed artefact. Nothing ships them; `pnpm dc:clean:apps` removes them.

The transferable point, for the record: a clean `PRAGMA foreign_key_check` proves nothing about a table that declares no foreign keys. If you want "nothing orphaned", enumerate the columns and check them.
