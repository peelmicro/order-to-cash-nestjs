# `observability_reliability` — Requirements (assessment #7)

> **The normative requirements for this feature are `R56` – `R60` and `R62` in [`specs/shared/requirements.md`](../shared/requirements.md) §8**, plus two requirements this feature closes that live in *other* sections because they were ratified deferrals from features that ran earlier: **`R16`** (§2, `outbox_and_idempotency`, deferred by that feature's open point 16) and **`R29`'s dead-letter clause** (§3, `order_saga_orchestrator`, deferred by that feature's `SO5`). ## 1. A correction to the brief that opened this pass, recorded for the gate

The task that opened this spec pass described Half A as "R56–R60, plus R29's deferred dead-letter half." Reading `specs/shared/test-matrix.md`'s own `R29` row (as instructed) surfaced a second ratified deferral this feature also owns: **`R16`**, `outbox_and_idempotency`'s own general consumer-retry-then-DLQ requirement, left `TODO` for this feature by that feature's spec (`specs/outbox_and_idempotency/requirements.md` open point 16, ratified at that feature's gate) and confirmed again at `order_saga_orchestrator`'s review (`progress/review_order_saga_orchestrator.md`'s D1, and `order_saga_orchestrator/design.md` §6.5 point 1: *"Wrap the fact handler's rejection path with attempts/backoff/DLQ — unchanged here"*). `R16` and `R29`'s DLQ clause are **related but distinct**:

- **`R16`** — *any* consumer's *own* fact processing throws (a domain exception, a malformed field that passes envelope-shape validation but fails a deeper parse — exactly the live incident below). The fix is a retry-then-DLQ wrapper around the consumer's processing, after which the **original fact** is acknowledged so its own partition is not blocked.
- **`R29`'s DLQ clause** — the fact was processed *successfully* (dedup recorded, aggregate advanced, a downstream RPC command enqueued), but that **downstream command** keeps failing until the saga's own in-line retry (`SO4`) is exhausted and the command **parks** (`SO5`). The fix is: on that park transition, dead-letter the *triggering* fact (for visibility) and record a saga-failure entry in the timeline — **without** disturbing `SO5`'s existing indefinite capped-backoff retry, which keeps the saga self-recovering.

Both are this feature's to close. `design.md` §2 argues they share one mechanism (the retry-then-DLQ wrapper) with one feature-specific extra step for `R29`'s case (the timeline fact), rather than two unrelated pieces of work.

## 2. The concrete incident this grounds in

`progress/current.md` records a live Phase-12 incident: a synthetic fact with a non-UUID `correlationId` on `otc.orders.facts.v1` halted the Orders saga consumer **permanently**, because the thrown error left the offset uncommitted; recovery needed manual `kafka-consumer-groups.sh` surgery. Reading `apps/orders/src/application/saga-fact-handler.ts` shows exactly where: `UniqueId.from(envelope.correlationId)` is called *inside* the transactional `work` callback passed to `IdempotentConsumer.runOnce`, well past `saga-facts.controller.ts`'s own envelope-shape guard (`parseFactEnvelope`, which only checks the seven envelope fields are present — a syntactically present but non-UUID `correlationId` passes it). The throw propagates out of `runOnce` (the whole transaction rolls back atomically, including the `processed_events` insert — confirmed by reading `idempotent-consumer.ts`), out of `SagaFactHandler.handle`, out of the `@CommandHandler`, out of `SagaFactsController.route`'s un-caught `await this.commandBus.execute(...)`, to `@nestjs/microservices`'s Kafka transport — which does not commit the offset on a thrown handler. Every redelivery repeats the identical throw, forever, on that partition. This is precisely `R16`'s failure shape, and every task below that touches the retry-then-DLQ wrapper carries a test that reproduces **this exact shape** — a non-UUID `correlationId`, not only a synthetic thrown error — per the binding instruction that grounds this pass.

## 3. Local requirements — `OR<n>` (Half A: reliability and observability)

These are genuine gaps: things `R16`, `R29`, `R56`–`R60` presume but do not pin down, which this assessment must make testable and concrete. None of them contradicts a shared requirement.

**OR1.** WHEN a fact consumed by `orders.saga`, `projector` or `notifications` (the three registered `ConsumerName`s) causes its processing to throw — including, but not limited to, a structurally valid envelope whose `correlationId` does not parse as a `UniqueId` — THE SYSTEM SHALL retry the fact's processing in line up to a configured maximum number of attempts (`FACT_RETRY_MAX_ATTEMPTS`, default 3) with exponential backoff (`FACT_RETRY_BACKOFF_MS`, default 500 ms, doubling), and on exhausting them SHALL publish the **unmodified original envelope** to `<source-topic>.dlq` annotated with `x-failed-consumer`, `x-attempts`, `x-error`, `x-original-topic`, `x-first-failed-at`, `x-failed-at` and the current trace context (`asyncapi.yaml`'s `DeadLetterHeaders`), and SHALL then acknowledge the original message so its partition is not blocked (refines `R16`'s "configured maximum" with this assessment's concrete policy, the same way `SO4` refined `R29`'s retry clause).

**OR2.** THE SYSTEM SHALL realise OR1's retry-then-DLQ wrapper as a single canonical pattern, parity-guarded across every consuming service exactly as `IdempotentConsumer` already is (`outbox_and_idempotency` design.md §6.4, `OI12`) — never as a bespoke per-service retry loop — so that a future sixth consumer starts from a guarded copy rather than inventing its own.

**OR3.** WHEN a `saga_commands` row (design.md §6.3 of `order_saga_orchestrator`) transitions from `pending` or `sent` into `parked` for the **first** time for that row, THE SYSTEM SHALL, in addition to the existing park bookkeeping (`SO5`, unchanged): (a) publish the row's `triggering_event_id` fact to its source topic's `.dlq`, annotated per `DeadLetterHeaders` with `x-failed-consumer` naming the saga's own consumer identity and `x-error` describing the downstream command failure, and (b) append exactly one `order.saga_failed.v1` fact for the order, carrying the failed `command`, the attempt count and the last error, so the projector renders a saga-failure entry in the order timeline. THE SYSTEM SHALL perform (a) and (b) **at most once** per row — a later sweep cycle that re-parks the same row after another exhausted retry attempt SHALL NOT repeat either publication — and SHALL NOT alter `SO5`'s indefinite capped-backoff retry of the underlying command in any way.

**OR4.** WHEN a message is published on the RPC transport (a saga command, a stock check, a gateway RPC) or the fact stream, THE SYSTEM SHALL inject the current W3C `traceparent` (and `tracestate`, if set) into that message's headers; and WHEN such a message is received, THE SYSTEM SHALL extract that context and continue the trace rather than starting a new one — refining `R57` with the concrete header fields already reserved for this by `asyncapi.yaml`'s `FactHeaders`/`DeadLetterHeaders` and by the `trace_parent` column `outbox_and_idempotency` provisioned, nullable and unused, specifically for this feature (`outbox_and_idempotency` design.md §3.3).

**OR5.** THE SYSTEM SHALL export every span and metric over OTLP to the already-provisioned OpenTelemetry Collector (`infra/otel-collector`), SHALL NOT expose a separate per-service Prometheus-format scrape endpoint, and Prometheus SHALL scrape metrics from the Collector's own exporter only — refining `R59`'s "expose metrics" with the concrete mechanism this repository's infrastructure was already built for (`infra/prometheus/prometheus.yml`'s `otel-collector` job; its commented-out per-application `static_configs` block is superseded, not activated — see `design.md` §5's open point).

**OR6.** THE SYSTEM SHALL expose `GET /health/live` and `GET /health/ready` on every service (not the Gateway alone), each service's readiness check consulting exactly the dependencies `R60` names that this service actually has (write model, fact stream, RPC transport — the Gateway's own existing checks, read model and RPC transport, are unchanged), generalising the `HealthCheck`/`HealthController` shape `apps/gateway` already established rather than inventing a second one.

## 4. Local requirements — `RI<n>` (Half B: `orders.create` requestId idempotent replay)

**RI1.** THE SYSTEM SHALL persist, for every accepted `orders.create` request that supplies a `requestId`, that `requestId` against the created order, under a uniqueness constraint that admits at most one order per `requestId`.

**RI2.** WHEN `orders.create` is received carrying a `requestId` for which a committed order already exists, THE SYSTEM SHALL perform no reference-data resolution, no stock check and no write, and SHALL return that order's original reply immediately (an optimisation over `R62`'s correctness requirement, not a substitute for RI3's guarantee under concurrency).

**RI3.** WHERE two `orders.create` requests carrying the same, not-yet-committed `requestId` are processed concurrently, THE SYSTEM SHALL let exactly one of them commit a new order, SHALL cause the other to detect the uniqueness constraint of RI1 rather than commit a second order, and SHALL then have the losing request return the winning order's reply — never an error, and never a second order — by re-reading the now-committed row for that `requestId` (the same "unique-index-as-serialisation-point, then resolve to the record that won" mechanism `billing_invoicing`'s `payments.payment_reference` constraint already uses for a **structurally different** case — see `design.md` §3's stated divergence from that precedent).

**RI4.** WHERE `requestId` is omitted from `orders.create`, THE SYSTEM SHALL place a normal order exactly as today, performing no lookup against RI1's constraint and no deduplication.
