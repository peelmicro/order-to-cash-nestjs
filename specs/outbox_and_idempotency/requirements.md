# `outbox_and_idempotency` — Requirements

> **Feature 14, phase 8, `"sdd": true`.** The transactional outbox (no dual-write), the polling relay that publishes facts to Kafka, and the idempotent-consumer pattern every fact subscriber in this system will reuse.

## 1. Requirements implemented from the shared specification

This feature implements the shared EARS range **`R11` – `R18`** — [`specs/shared/requirements.md`](../shared/requirements.md) §2 `outbox_and_idempotency` — **except `R16`**, whose realisation is deferred to feature 27 (see the deferral note below).

Those requirements are **not restated here**. `specs/shared/requirements.md` is the single authority for their wording and is reused verbatim by assessments #8 (.NET) and #9 (FastAPI); a copy in this file would drift the moment either document is touched. Read them there, and read the envelope contract they cite in [`specs/shared/domain-model.md`](../shared/domain-model.md) §7.1 and the three idempotency layers in [`specs/shared/saga.md`](../shared/saga.md) §6.

| Shared id | One-line reminder (authority is the shared file) | Realised in this feature by |
|---|---|---|
| **R11** | Complete envelope on every fact; `eventType` matches `<aggregate>.<fact>.v<n>` | Already **DONE** at kernel level (`assertValidDomainEventEnvelope`). This feature makes it true *at rest and on the wire*: every envelope field becomes a persisted outbox column (see **OI1**) and the relay serialises the row into the generated `Envelope` type of `@otc/contracts` |
| **R12** | `correlationId` = order id; `causationId` = the causing fact's `eventId` or the causing command's id | The `causation_id` column added to all three `outbox` tables by this feature's coordinated migration (`design.md` §3.1) — today `causationId` is generated by the aggregate and then **thrown away** at persistence time |
| **R13** | Aggregate state and outbox records commit in **one** transaction, or neither | The `UnitOfWork` port + `OrderRepository.save(order, tx)` + `OutboxRecorder` (`design.md` §4) |
| **R14** | Only the relay publishes; a record is stamped only after the broker acknowledges; unstamped records are republished | `OutboxRelay.runOnce()` — claim, publish, stamp-after-ack, all inside one write-model transaction (`design.md` §5) |
| **R15** | `correlationId` is the fact-stream partition key, giving per-order ordering | `KafkaFactPublisher` keys every message by the row's `correlation_id`, with the idempotent producer enabled so a client-internal retry cannot reorder a partition (**OI7**) |
| **R16** | Consumer retry with backoff, then `<topic>.dlq`, then ack | **Deferred to feature 27** `observability_reliability` — see below |
| **R17** | (`eventId`, consumer) recorded in the **same transaction** as every effect | `IdempotentConsumer.runOnce(...)` writing `processed_events` inside the same `UnitOfWork` as the handler's effects (`design.md` §6) |
| **R18** | A redelivery is acknowledged with no mutation, no fact, no command | The duplicate branch of `IdempotentConsumer.runOnce(...)`, which rolls back and reports `duplicate` without invoking the handler |

### The `R16` deferral — ratified, not overlooked

`R16` sits inside the shared `R11`–`R18` block, but its behaviour (retry with backoff, dead-letter after N attempts, then acknowledge) is **consumer-side reliability**, and `feature_list.json` gives it to feature 27 (`observability_reliability`: *"failed processing lands on `<topic>.dlq` after N attempts"*). `specs/shared/test-matrix.md` agrees: the `R16` row names `projector/integration/dead-letter.spec`, a file that belongs to a service this feature does not touch.

This feature therefore ships with the `R16` row still `TODO`, and **matrix rule 3** ("a feature cannot be marked `done` until every one of its rows is green") is read here as *every row this feature owns*. Feature 14 is complete when **`R12`, `R13`, `R14`, `R15`, `R17`, `R18`** are green (`R11` already is). The seam feature 27 inherits is written down in `design.md` §7 so nothing about it is left to discovery.

## 2. Feature-local requirements

These state behaviour the shared specification genuinely leaves open, discovered while reading `specs/shared/requirements.md` §2 and `saga.md` §6 against the three committed `outbox` / `processed_events` schemas, the `Order` aggregate's `pullDomainEvents()` surface, and the two binding advisories this feature inherits (`progress/review_db_orders.md` § advisory notes, echoed by `review_db_fulfillment.md` and `review_db_billing.md`). Each is recorded with its rationale in [`progress/spec_outbox_and_idempotency.md`](../../progress/spec_outbox_and_idempotency.md) §3 (open-points table).

**Id namespace.** Local ids are prefixed `OI` deliberately, for the reason `orders_aggregate` established: the shared range `R1`–`R61` is frozen and contiguous, ids are never renumbered, and #8/#9 cite the same numbers. `OI<n>` cannot collide with `R<n>`, and its traceability lives in §3 of this file rather than in `specs/shared/test-matrix.md`, which stays the trilogy contract. Any `OI` that proves genuinely stack-agnostic is a **promotion candidate** for the shared spec at feature 38 (`final_checkpoint`), not before — §5 lists the four.

**OI1.** THE SYSTEM SHALL persist, for every outbox record, every field of the R11 envelope — `eventId`, `eventType`, `aggregateId`, `correlationId`, `causationId`, `occurredAt` and `payload` — such that the relay reconstructs the published envelope from the stored record alone, inferring, defaulting or regenerating no field at publication time; and IF any envelope field is absent from a record about to be published, THEN THE SYSTEM SHALL fail the publication of that record rather than publish an incomplete envelope. *(Resolves inherited advisory 1: `causationId` is currently generated by the aggregate and discarded by persistence, so R12's causal chain is unrecoverable after the fact.)*

**OI2.** THE SYSTEM SHALL order the relay's publication of unpublished records by a **strictly increasing, tie-free sequence assigned at insertion**, so that two records written by one transaction — which necessarily share a `correlationId` and may share an identical `occurredAt` — are always published in the order the aggregate appended them, and so that the publication order of any two records of one write model is the same on every poll and on every relay instance. *(Resolves inherited advisory 2: `(published_at, occurred_at)` is nondeterministic because rows written in one transaction tie, and finer timestamp precision would only make the tie less likely, never impossible.)*

**OI3.** THE SYSTEM SHALL select the records to publish by the **absence of a publication stamp** and never by a stored high-water mark of the ordering sequence, so that a record whose transaction committed after a higher-sequence record had already been published is still found and published on a later poll.

**OI4.** WHILE two or more relay instances poll one write model concurrently, THE SYSTEM SHALL grant each unpublished record to at most one instance per poll cycle, so that no record is published twice as a result of concurrent claims and no record is skipped because another instance holds it.

**OI5.** IF a relay instance terminates, loses its database connection or fails after claiming records and before stamping them published, THEN THE SYSTEM SHALL make those records claimable again without operator action, without a lease-expiry wait and without a compensating sweep, and SHALL publish them on a later poll — accepting the resulting duplicate publication as the at-least-once contract of R14.

**OI6.** WHILE a poll cycle of one relay instance is in progress, THE SYSTEM SHALL NOT begin a further poll cycle in that instance, so that the configured poll interval can never cause overlapping cycles to compete for the same records.

**OI7.** THE SYSTEM SHALL configure the fact-stream producer so that a retry performed inside the producer client can neither reorder the records of one partition nor create a broker-side duplicate of a record the broker already accepted.

**OI8.** IF the broker rejects or fails to acknowledge a claimed batch, THEN THE SYSTEM SHALL leave every record of that batch unpublished, SHALL log the failure with the `correlationId` and `eventId` of the affected records, SHALL retry the same records on the next poll, and SHALL NOT skip them, drop them, reorder them or publish a later record ahead of them.

**OI9.** WHEN a unit of work that persisted an aggregate and its outbox records is rolled back, THE SYSTEM SHALL leave no outbox record and no aggregate change behind, and a retry of the same operation SHALL produce exactly one outbox record per emitted fact — never zero, which is what a retry driven from the already-drained in-memory aggregate instance would produce.

**OI10.** IF the same (`eventId`, consumer) pair is delivered concurrently to two consumer instances of one write model, THEN THE SYSTEM SHALL apply the handler's effects exactly once — one delivery committing its effects together with its dedup record, the other observing the dedup record and reporting a duplicate without applying any effect.

**OI11.** THE SYSTEM SHALL keep the `outbox` and `processed_events` definitions — every column, type, nullability, key and index — identical in all three write models, and SHALL prove that identity mechanically rather than by inspection.

**OI12.** THE SYSTEM SHALL keep every per-service copy of the idempotent-consumer pattern in textual agreement with one designated canonical copy — identical in every statement, name, type and comment, normalising only the per-copy banner in which a copy declares which canonical governs it — and SHALL prove that agreement mechanically rather than by inspection; and IF a write model that consumes facts carries no copy of the pattern, or a copy diverges from the canonical outside its banner, or the canonical acquires a service-specific name or import that another service could not adopt verbatim, THEN THE SYSTEM SHALL fail the check. WHERE a component's dedup ledger is not a MySQL `processed_events` table and the pattern therefore cannot be copied verbatim (the projector's MongoDB ledger, feature 23's choice for notifications), THE SYSTEM SHALL require that component's variant to name the canonical copy and state its divergence in prose, and SHALL exclude it from the textual comparison. *(Guards the duplication chosen in `design.md` §6.3 with a check rather than with discipline — the same instrument `OI11` applies to the three migration bodies.)*

## 4. Acceptance (from `feature_list.json`)

The backlog's four acceptance bullets map onto the requirements above, with no bullet left unowned:

| Acceptance bullet | Requirement |
|---|---|
| aggregate row and outbox row written in one transaction | R13, OI9 |
| relay publishes to Kafka keyed by `correlationId` and stamps `publishedAt` | R14, R15, OI1, OI2, OI3, OI7, OI8 |

`OI11` serves none of the four bullets directly: it exists because the three write models must not drift while this feature changes all three (`progress/review_db_billing.md` §3 diffed them by hand; this feature automates that diff).

`OI12` likewise serves no bullet directly, and for the sibling reason: the fourth bullet is satisfied by the Orders copy alone, but that copy is the reference four more components will duplicate (`design.md` §6.3), and a duplication guarded only by discipline is a defect waiting for feature 17. It automates a diff that would otherwise never be performed at all — `OI11` automates one the reviewers had been doing by hand.

## 5. Promotion candidates for `specs/shared/`

Four of the twelve local requirements are not stack-specific: they are gaps in the shared contract that #8 (.NET) and #9 (FastAPI) will hit unchanged, and those assessments read **only** `specs/shared/`. Left local, they would produce three implementations that genuinely differ in behaviour — the outcome the trilogy exists to rule out. They are recorded here as **promotion candidates** for feature 38 (`final_checkpoint`), the only feature allowed to extend the frozen shared range. Nothing in `specs/shared/` is edited by this feature.

| Local id | What it says | What promotion would change in `specs/shared/` |
|---|---|---|
| **OI1** — the envelope must survive storage | Every envelope field is stored, so the relay reconstructs the envelope without inference | `R11` constrains the *published* envelope only. Promotion would add the at-rest half — that a fact's causal metadata is durable from the moment the producing transaction commits — which is what makes `R12`'s "reconstructible from the facts alone" claim true after a crash. Any assessment can otherwise satisfy `R11`/`R12` at publish time by inventing a `causationId`. |
| **OI2** — deterministic publication order | Publication order is a strictly increasing, tie-free insertion sequence | `R14` says nothing about the order in which unpublished records are drained, and `R15` only fixes the partition key. Two facts written by one transaction (`asyncapi.yaml` explicitly relies on this for `payment.received.v1` → `credit.released.v1`) can therefore be published in either order by a conforming implementation. Promotion would state the ordering obligation of the relay, leaving *how* to each stack. |
| **OI4** + **OI5** — exclusive claim and crash recovery | Concurrent relays never publish the same record twice through concurrent claims; a crashed relay's records become claimable again with no operator action and no lease wait | `R14` accepts at-least-once but never says the relay may run more than once, nor what happens to work in flight when it dies. This is the single most likely place for three different answers (advisory lock, lease column, leader election) with three different failure profiles. |
| **OI10** — concurrent duplicate delivery | Two concurrent deliveries of one event to one consumer produce exactly one effect | `R17`/`R18` describe redelivery **sequentially** ("has already been recorded"). Neither forbids two in-flight deliveries from both passing a read-then-write check and both applying effects. Promotion would state the exactly-once-effect obligation, leaving the mechanism (unique constraint, serialisable isolation, lock) to each stack. |

`OI3`, `OI6`, `OI7`, `OI8`, `OI9`, `OI11` and `OI12` are **not** proposed: `OI3`/`OI6`/`OI9` are consequences of how *this* relay and *this* unit of work are built, `OI7` is a property of a specific broker client, `OI8` is a scoping statement about what feature 27 owns, `OI11` is about three databases that exist because #7 chose a database per service, and `OI12` guards a duplication that exists only because #7's `CLAUDE.md` forbids a third shared runtime package — #8 can share one project and #9 one module, leaving them nothing to keep in parity.
