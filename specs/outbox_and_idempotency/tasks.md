# `outbox_and_idempotency` — Tasks

> Ordered. Each task is small enough to verify on its own. The implementer ticks `[x]` as it goes and stops at the first task it cannot complete honestly. Tests are written **inside** the loop — a task that adds behaviour and the task that proves it are adjacent, never batched to the end.
>
> **Order of groups: A → B → C → D → E → F → G → H → I.** Group A (the three-database migration) comes first on purpose: every later group typechecks against the new columns, and the collateral repairs (B) must land in the same breath as the schema that breaks them.
>
> Requirement ids: shared `R11`–`R18` ([`specs/shared/requirements.md`](../shared/requirements.md) §2, `R16` deferred to feature 27); local `OI1`–`OI12` ([`requirements.md`](./requirements.md) §2). Design: [`design.md`](./design.md).
>
> **Before A1, recreate the databases.** `ADD COLUMN ... NOT NULL` with no default cannot be applied to a table that already holds rows: `pnpm dc:clean:infra` (or `docker compose -f docker-compose.infra.yml down -v`) → `pnpm dc:up:infra` → migrate → seed. Same procedure feature 13 used for `order_items.description`; record it in the progress file (I5).
