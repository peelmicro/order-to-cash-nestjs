# `fulfillment_stock` — Requirements (assessment #7)

> **The normative requirements for this feature are `R30` – `R36` and `R61` in [`specs/shared/requirements.md`](../shared/requirements.md) §4**, elaborated by [`specs/shared/domain-model.md`](../shared/domain-model.md) §4 (the `StockItem` aggregate, the `Reservation` child entity, invariants **F1** – **F5**, the reservation lifecycle §4.2), [`specs/shared/saga.md`](../shared/saga.md) §2 (the command vocabulary and its idempotency keys), §4.1 (*"the race is real and intentional"*), §6 layer 3 (idempotent responders) and [`specs/shared/asyncapi.yaml`](../shared/asyncapi.yaml) (the five `fulfillment.stock.*` request/reply schemas and the three `stock.*` fact payloads). They are **not restated here** — this file adds only the local requirements (`FS<n>`) for gaps the shared spec leaves to each assessment, and the traceability for them.
>
> **Scope note on `R36`.** `R36` (`despatch.create`) is listed in the shared §4 range but its responder is feature 18 `fulfillment_despatch`. This feature delivers only the aggregate half it depends on — `consume(orderReference)` on `StockItem` and the `reserved → consumed` edge of the lifecycle (`R35`) — and leaves the `R36` matrix row `TODO` for feature 18 to flip. Likewise `R61`'s *API* half (`api/stock-replenishment.spec`) belongs to the Gateway (feature 25); only its domain-unit half flips here.
>
> Related shared requirements this feature composes with but does not own: `R13`/`R14`/`R15` (the outbox, the relay and the partition key — the Fulfillment copies of the relay are proven against them here, the rows stay owned by feature 14), `R17`/`R18` (the idempotent-consumer pattern — copied, not exercised: Fulfillment consumes no fact in this feature), `R29` (the orchestrator's retry and `(orderReference, operation)` idempotency — the *responder* side of that contract is this feature's `FS5`, `FS9`), `R12` (`causationId` chains — `FS3`).

## 1. Local requirements — `FS<n>`

These are genuine gaps: things `R30` – `R36`/`R61` presume but do not pin down, which this assessment must make testable. None of them contradicts a shared requirement. `FS1` and `FS2` are **Orders-side** requirements (the binding advisory D1 and the correlation header the responder needs), delivered by this feature's task group A because feature 17 is the first real responder that exposes them.

### 1.1 Orders side — what the first real responder forces

**FS1.** WHEN the orchestrator processes a fact whose step owes a command for an order that **already** holds a `saga_commands` row for the same `(order_id, command)` pair — a distinct-`eventId` duplicate of a fact whose precondition still holds — THE SYSTEM SHALL commit the fact's transaction without inserting a second row and without failing, SHALL treat the existing row as the owed command, and SHALL re-dispatch it on the fast path exactly as a freshly enqueued one (a `sent` row is a silent no-op, a `pending` or `parked` row is dispatched); THE SYSTEM SHALL NOT reject the consumer's transactional unit on the `(order_id, command)` unique key. *(Reviewer advisory D1 of `progress/review_order_saga_orchestrator.md` — reproduced as a consumer crash-loop on one offset; binding before `R16` is claimed at feature 27.)*

**FS2.** WHEN the orchestrator issues any of the five saga commands over the RPC transport, THE SYSTEM SHALL carry the request headers `x-correlation-id` = the order id and `x-request-id` = the id of the durable `saga_commands` row being dispatched, and SHALL carry the **same two values** on every in-line retry and every sweeper re-issue of that row (`asyncapi.yaml` `RpcHeaders`: *"a retry after a timeout reuses the same value, which is what lets a responder recognise a duplicate"*). The `stock.check` call made at order acceptance carries no `x-correlation-id` (no order exists yet).

### 1.2 Wire contract of the responders

**FS3.** WHEN Fulfillment emits a fact in response to a `stock.reserve` or `stock.release` command, THE SYSTEM SHALL set the fact's `correlationId` from the request's `x-correlation-id` header and its `causationId` from the request's `x-request-id` header (`R12`); IF either header is absent or is not a valid `UniqueId`, THEN THE SYSTEM SHALL reply `RpcError` `VALIDATION_FAILED`, SHALL mutate no stock item and SHALL emit no fact. `stock.check`, `stock.list` and `stock.replenish` require neither header.

**FS4.** THE SYSTEM SHALL accept each of the five `fulfillment.stock.*` requests as a **bare JSON** payload matching the AsyncAPI request schema — no framework packet envelope around it — and SHALL reply with a **bare JSON** success payload or a bare JSON `RpcError`, exactly as `asyncapi.yaml` documents the reply channels; a responder method never resolves with anything else and never rejects. *(The callers that exist today — Orders' `nats-stock-availability.adapter.ts` and `nats-saga-commands.adapter.ts` — send and decode exactly this shape; `design.md` §6.3 records why the framework's default reply shape does not satisfy it.)*

### 1.3 `stock.reserve` — idempotency, locking, the race, unknown products

**FS5.** WHILE reservation rows already exist for the request's `orderReference` (in any status), THE SYSTEM SHALL reply to `stock.reserve` with `outcome: already_reserved` carrying the existing reservation references, SHALL change no `reservedUnits`, SHALL create no reservation and SHALL emit no second `stock.reserved.v1` (saga.md §6 layer 3, `R29`'s responder half).

**FS6.** WHEN executing `stock.reserve`, THE SYSTEM SHALL acquire an exclusive row lock on every stock item named by the order's lines, in one statement ordered by `(companyCode, productCode)`, **before** evaluating availability or reading existing reservations, so that IF two `stock.reserve` commands for different orders compete for the last units of one item concurrently, THEN exactly one commits a reservation and emits `stock.reserved.v1` and the other emits `stock.rejected.v1` naming the shortage — never both reserving, never a deadlock between them.

**FS7.** IF a line was reported `sufficient` by an earlier `stock.check` and is no longer satisfiable when `stock.reserve` runs, THEN THE SYSTEM SHALL reject per `R33` exactly as it would have without the earlier check — the check is a non-locking read that holds nothing (`R31`) and its reply is never a promise; the rejection is a legitimate, intended outcome the saga compensates (saga.md §4.1), not an error.

**FS8.** IF any line of a `stock.reserve` request names a `productCode` for which no stock item exists under the request's `companyCode`, THEN THE SYSTEM SHALL treat that line as short with `available: 0`, SHALL create no reservation for any line (`R33`, **F3**), and SHALL emit `stock.rejected.v1` with `reason: unknown_product`; WHEN every line names a known item and at least one is short, the reason SHALL be `insufficient_stock`.

### 1.4 `stock.release` — the two edges `R34` leaves open

**FS9.** WHEN `stock.release` is received for an `orderReference` that holds **no** reservation row at all, THE SYSTEM SHALL reply `outcome: already_released` with an empty `released` list, SHALL change no counter and SHALL emit no fact — the same success no-op as `R34`'s all-already-released case, because an order that never held stock has nothing to unwind (saga.md §4.1).

**FS10.** IF `stock.release` is received for an order whose reservations are in status `consumed`, THEN THE SYSTEM SHALL reply `RpcError` `PRECONDITION_FAILED`, SHALL change no reservation, no counter and SHALL emit no fact (**F4**, `R35` — a consumed reservation is terminal; the goods left, and cancellation is impossible from `despatched` onwards per Table T-1).

### 1.5 The aggregate — consume, the derived counter, the fact's aggregate identity

**FS11.** WHEN `consume(orderReference)` is invoked on a stock item holding reservations in status `reserved` for that order, THE SYSTEM SHALL set those reservations to `consumed`, SHALL decrease both `units` and `reservedUnits` by their total, and SHALL append **no** domain event — the fact that accompanies consumption is `order.despatched.v1`, emitted by the `DespatchAdvice` aggregate in feature 18 (domain-model.md §4.2, Table row `reserved → consumed`).

**FS12.** THE SYSTEM SHALL reconstitute a `StockItem` from its stored `units`, `reservedUnits` and the reservation rows loaded with it, and after every committed `stock.reserve`, `stock.release` and `consume` transaction THE SYSTEM SHALL leave `reserved_units` equal to the sum of `units` over that item's reservations in status `reserved` (**F2** — the counter is a derived cache of the ledger and is mutated only in step with it, inside the same transaction).

**FS13.** THE SYSTEM SHALL set the `aggregateId` of `stock.reserved.v1` and `stock.rejected.v1` to the id of the stock item named by the **first line** of the request that resolves to a known item, and the `aggregateId` of `stock.released.v1` to the id of the stock item of the first reservation released, so that every order-scoped Fulfillment fact carries a real aggregate identity (domain-model.md §7.1) even though one `stock.reserve` transaction touches one stock item per line (**F3** — see `design.md` §4.2 for the documented tension with §8 rule 6).

### 1.6 `stock.replenish` and `stock.list`

**FS14.** IF any line of a `stock.replenish` request names a `productCode` with no stock item under the request's `companyCode`, THEN THE SYSTEM SHALL reply `RpcError` `NOT_FOUND` naming that product and SHALL replenish **no** line of the request (all-or-nothing, so a partially applied top-up cannot exist); WHEN every line is known, THE SYSTEM SHALL apply `R61` to each and reply the affected items as `StockView`s.

**FS15.** WHEN `stock.list` is received, THE SYSTEM SHALL reply `StockView` items with `availableUnits = units − reservedUnits`, ordered by `(companyCode, productCode)`, paged per `PageRequest` defaults (`page` 1, `pageSize` 25, max 200), filtered by `companyCode` and `productCode` when present, and WHERE `belowThreshold` is `true` SHALL return only items whose `availableUnits < lowStockThreshold`; the query SHALL mutate nothing and take no lock.

### 1.7 The facts leave through Fulfillment's own outbox

**FS16.** THE SYSTEM SHALL write `stock.reserved.v1`, `stock.rejected.v1` and `stock.released.v1` as outbox records in the **same transaction** as the reservation rows and `reserved_units` changes they describe (`R13`), and SHALL publish them to `otc.fulfillment.facts.v1` **only** through Fulfillment's own outbox relay, keyed by `correlationId` (`R14`, `R15`) — no responder, handler or aggregate publishes directly.

### 1.8 First boot against the live stack

**FS17.** WHEN the Fulfillment responders first start against a compose stack whose `otc_orders.saga_commands` holds `parked` `stock.reserve` rows, THE SYSTEM SHALL answer the sweeper's next re-issue of each row so that, without operator action, each such order gains reservation rows, one `stock.reserved.v1` (or `stock.rejected.v1`) in `otc_fulfillment.outbox` stamped published, and advances in Orders to `stock_reserved` with a new `credit.hold` row that parks (Billing does not exist yet) — or to `cancelled`/`stock_rejected` with no `stock.release` row. *(Designed in `design.md` §11; verified live, not by an automated test.)*

## 3. Promotion candidates (for a later shared pass, not edited now)

- **`FS2`/`FS3` — the correlation carrier.** `asyncapi.yaml`'s `RpcHeaders` documents `x-correlation-id` and `x-request-id`, but no shared requirement *obliges* the caller to send them or the responder to derive `correlationId`/`causationId` from them. Without that sentence, #8/#9 could satisfy `R12` for Orders-emitted facts and have no way to satisfy it for Fulfillment/Billing-emitted ones (the request payloads carry only `orderReference`). Candidate wording for `requirements.md` §2: *"WHEN a command concerning a known order is issued over the RPC transport, THE SYSTEM SHALL carry the order id as `x-correlation-id` and a per-command-record id as `x-request-id`, and a responder SHALL stamp the facts it emits in response with that `correlationId` and that `causationId`."*
- **`FS13` and domain-model.md §8 rule 6.** *"One transaction mutates exactly one aggregate instance plus its outbox records"* and **F3** *"either every line of the order is reserved, or none is"* cannot both hold literally when an order's lines name different products (one `StockItem` per product). The shared model should say which yields — this assessment says F3 does, with a deterministic lock order and a single carrier aggregate for the fact's identity (`design.md` §4.2).
- **`FS5` (repeat-reserve against a released/consumed order).** saga.md §6 says a second `stock.reserve` "returns the existing reservation without double-reserving" but does not say what "existing" means once those reservations are terminal. This assessment answers *any* reservation rows for the order, whatever their status. Worth one sentence in saga.md §6 so #8/#9 do not re-reserve after a release.
- **`FS9`/`FS10`** (release of a never-reserved order; release of a consumed order) are edges `R34` leaves open; both are cheap to state in the shared §4.
- **Consumer-name vocabulary.** The shared § Vocabulary lists `orders.saga`, `projector`, `notifications` only. Correct today (Fulfillment consumes nothing), but the day Fulfillment or Billing gains a consumer the closed set must grow in the shared file first — recorded so it is not invented per service.
